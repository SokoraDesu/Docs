# Settings

## How settings work

Sokora has a single file that declares in an object all settings the bot knows of (so-called “setting definition“). The database isn’t aware of the definition so we can update them freely at any time (as long as any breaking change is migrated accordingly).

A setting holds:

- Always
    - A machine-readable key
    - A human-readable description
    - A data type
    - An emoji tied to it
- If you want to
    - A default value
    - A precondition
    - If it is iterable

Most of that should make sense right away. Some things might not, though:

### Data types

Supported types are:

```ts
// where Maybe<T> = T | undefined
{
  BOOL: boolean;
  INTEGER: number;
  mINTEGER: Maybe<number>;
  TEXT: string;
  mTEXT: Maybe<string>;
  TIMESTAMP: Temporal.Instant;
  mTIMESTAMP: Maybe<Temporal.Instant>;
  CHANNEL: string;
  mCHANNEL: Maybe<string>;
  USER: string;
  mUSER: Maybe<string>;
  ROLE: string;
  mROLE: Maybe<string>;
  SELECT: string;
  OBJECT: Record<string, "(any supported type, except other objects)">;
}
```

!!!note "Why so many strings?"
    Types are readable at runtime. User is a string because it is an ID, so things like PSE first check the type then use the string accordingly. So are role and channel.

    Select is a string because it holds a string value, and the name implies that it’s _not_ a free-form string and that you have a set of choices.

### Being iterable

Settings can be iterable. This means, if the type is `TEXT` (`string`) and `iterable` is `true`, effectively the type is `string[]`. An iterable setting can hold more than one value. Usually you use this with `SELECT` to make it a multiselect, with `ROLE|USER|CHANNEL` to allow more than one option, or with an `OBJECT` to make it a list of objects.

So-called iterable objects are quite :sparkles: special :sparkles: (and a PITA to work with), but we’ve done our best at making them work seamlessly. You will note some differences though:

- Objects within the array have a GUID. It’s autogenerated *but* you have to manually add it as a parameter to the object declaration for typing to work.
- Usually when getting an iterable setting you just get the array. By default this is the same here, but you can pass an individual object’s GUID to get that one specifically.
- You need to declare a `naming` function and a `sorting` function in the setting definition, as they’re needed for PSE. FWIW, these callbacks are not typed, they’re `any`, so you have to cast the type. Haven’t found a fix so far.
- You cannot nest objects (without PSE breaking beyond comprehension).

!!!tip "Fun fact"
    Yep, they’re indeed a PITA. In fact, if you go to sokora.org and scroll down a little, the section talking about our settings system has a barely visible easter egg that says “An embed\*is all it takes… \*and days of pain spent by the people who made this work“. Most of said pain came from here.

Annoyance aside, they enable a great end user experience, so get used to them and don’t think twice if you think your next feature contribution could use an object or an iterable object setting.

## Using settings

The API couldn’t be simpler.

```ts
await getSetting(
  "entity ID",
  "category",
  "setting"
);

await setSetting(
  "entity ID",
  "category",
  "setting",
  value
);
```

Entity ID is a *user ID* for user settings and a *guild ID* for server settings. Category and setting are properly typed and your code editor (if LSP capable) will tell you what goes there! And `value` for `setSetting` is typed as well.

`getSetting` has a fourth argument, for when you need to reference a specific object within an iterable object setting. You can pass the GUID of the setting to it. More on this later.

#### Modifying settings

You have a *database* file called `settings.ts` which defines all settings. Settings are added in so-called setting declarations, which look like this:

```ts
export const defCategory = {
  setting_one: {
    type: "BOOLEAN",
    val: true,
    desc: "Whether setting one is enabled. Defaults to true.",
  },
  setting_two: {
    type: "OBJECT",
    iterable: false,
    desc: "Nested setting.",
    properties: {
      something: {
        type: "BOOL",
        val: false,
        desc: ":)",
      },
      something_two: {
        type: "INTEGER",
        desc: ":) 2",
        val: 60,
      },
    },
  },
} satisfies SettingDefinitionRecord["settings"];
```

Each category is defined as `defName`, and is an object typed `SettingDefinitionRecord["settings"]`. Individual properties are documented with TSDoc so it’s easy to get how things work.

If you create a new `def`, add it to the main object.

```ts
export const settingsDefinition = {
  leveling: {
    description: "Customize the behavior of the leveling system.",
    settings: defLeveling,
  },
  moderation: {
    description: "Change Sokora’s settings related to moderation.",
    settings: defModeration,
  },
  // add it here...
} as const;
```

Also specify if it’s a user category or a server category by adding its key to either of the arrays below `settingsDefinition`.

```ts
export const serverSettingsKeys = [
  "easter",
  "leveling",
  // ...
] as (keyof TS)[];
export const userSettingsKeys = [
  "topgg",
  "leveling",
  // ...
] as (keyof TS)[];
```

And if you’re defining an iterable object, add the special `$` property to it (copy paste this):

```json
$: {
  "type": "TEXT",
  "desc": "",
  // val is needed, whatever you put inside will be ignored
  "val": ""
}
```

It’s the GUID we told you about earlier.
